# Proactive offer replay evidence

These files retain the model tool names and arguments from the coordinator's
production r9f attempt artifacts. `source` identifies the original attempt and
`sha256` identifies its complete file. The original records also contain grading,
timing, rendered client output and account fixtures; only the model calls are
needed at the model-service port. Existing redactions are preserved.

`R9fOfferReplayTests` drives the production handler, gateway and previewer with the
captured strict arguments. `R9fReadOfferReplayTests` drives the production read
executor with captured calls and repository-port account facts. Selector IDs are
resolved from the real typed candidate producer; the attempts retained the visible
View details choice but did not retain its raw selection JSON.

The bilingual read cases reuse the captured structured call with a negotiated
locale. They do not classify or route the person's message. Invalid-schedule repair
uses a second captured valid call for the same operation and title. Separate
prompt assertions pin guidance for model choices that a replay cannot measure.
The live gate remains the coordinator's release check.

The `R9g` captures retain the corresponding production run's tool names and
arguments with the complete source-file hash. `R9gOfferReplayTests` uses them at
the model-service port to prove the missing-value repair and the calendar-window
rejection. The reminder-conflict replay fills the independently missing frequency
quantity before testing the sibling reminder defect; its single repair removes
the conflicting fixed suggestion while keeping the repeat interval. No captured
result is used as a test double for the gateway or previewer.

Legacy calendar and brain-dump replays supply `window: month` to keep exercising
their existing calendar projection. The r9g day-call capture remains unchanged
and must be rejected. Legacy placeholder replays with missing suggestion values
now perform the same single repair required by the contract.
